# 源码阅读训练指南

> **版本**：v2.1 — 每日 Task1/2/3 结构 — 以「六项跃升标准」为唯一毕业准则  
> **训练目标**：读框架 / 读项目的**行为跃升**，不是读 LangChain 本身。  
> **练手对象**：LangChain（`/home/zym/langchain`）。  
> **时间投入**：每天 3 小时，共 12 周（84 天）。  
> **毕业标准**：见下文 **§ 六项跃升标准** — 交付物齐全只是过程，**闭卷行为测试通过**才算毕业。

## 六项跃升标准（北极星）

跃升不是感觉，是**行为变化**。以下 6 条是 12 周训练的唯一终点；所有日课、周课、交付物均为此服务。

| # | 标准 | 可观测行为 | 毕业阈值 |
|---|------|------------|----------|
| **①** | **30 分钟出地图** | 陌生 repo → README → pyproject → `__init__.py` → 包依赖图 + public API 清单 | 闭卷计时 ≤30min，地图可让他人看懂 |
| **②** | **15 分钟定位扩展点** | 回答「接新 LLM / 存储 / 中间件，最少改哪几个类？」 | 闭卷计时 ≤15min，指到具体基类/文件，不靠猜 |
| **③** | **1 小时跟完主链路** | 公开 API → 返回，写数据形变表 | 闭卷计时 ≤60min，迷路 ≤3 次 |
| **④** | **读设计，不只读流程** | 见 `@deprecated`、包拆分、Middleware 能说出**为什么** | 闭卷口述 3 个设计案例，含「为何」 |
| **⑤** | **框架 / 项目读法自动切换** | LangChain 外→内；imooc-llmops 入口→主链路 | 同一小时內各完成 1 次，不混用读法 |
| **⑥** | **二手资料降级为辅助** | 先读源码形成判断，再用文档/课程**验证** | 完成 5 次「预测→读码→对照」，命中率 ≥60% |

> **硬规则**：任一标准期末未达标 → **延长对应周次**，不得带缺口毕业。

## 如何使用本文档

1. **六层模型是路径，六项标准是终点** — 不要为填交付物而读。
2. **每个学习日按 Task1 → Task2 → Task3 顺序做** — Task3 是 Task1/2 的整理，不是另起炉灶。
3. **验收日**：Task2 含闭卷验收；Task3 记录计时与通过与否。
4. **未通过验收则延长该步** — 天数只是标签，标准才是问题。
5. **读码日志**：每个学习日必写（Task3）；交付物按该步规划有则更新。

### 每日 Task 结构（约 3 小时）

| Task | 主旨 | 子项 |
|------|------|------|
| **Task 1 · 读** | 输入 | **1.1 读什么** / **1.2 为何要读** / **1.3 本日刻意训练的阅读动作** |
| **Task 2 · 练** | 动手验证 | **2.1 练什么**（对照 / 问答 / 闭卷 — **要回答的问题写在这里**）/ **2.2 为何要练** / **2.3 限制条件** |
| **Task 3 · 整理** | 输出 | **3.1 交付物**（Task1/2 成果写入）/ **3.2 读码日志**（必写）/ **3.3 误判复盘** |

> **原则**：Task2 的练（含问答、对照、闭卷）结果应能直接粘贴进 Task3 的交付物；不要读完后另起一套再写一遍。
>
> Day 1–84 的 `1.3 / 2.3 / 3.3` 见下文《84 天逐日能力训练矩阵》。执行日课时，必须把对应行写入当天日志；原日课只规定材料范围，不单独构成完整训练。

# 源码阅读能力训练操作系统

> 六层模型回答「先读哪一类材料」；本节回答「打开文件以后究竟怎样读，为什么这样读，以及如何确认能力真的提高」。
> 84 天训练的核心不是记住 LangChain，而是反复执行以下动作，直到面对陌生仓库也能自动使用。

## 1. 能力拆解：源码阅读不是一种能力

| 能力 | 核心问题 | 可观察动作 | 为什么要练 |
|------|----------|------------|------------|
| **定向** | 我现在在哪一层？先忽略什么？ | 用 README、目录、依赖和 public API 在 30min 内画地图 | 没有地图就容易随机跳文件，工作量会指数增长 |
| **定位** | 哪个符号最可能是入口或扩展点？ | 先写搜索词，再用 `rg`、定义跳转、引用查找定位 | 搜索策略决定读码速度；只靠 IDE 漫游不可复现 |
| **切片** | 当前问题最小需要读哪些代码？ | 写出「必读 / 暂不读」列表，控制阅读边界 | 阅读能力不是读得多，而是用最小代码量回答问题 |
| **追踪** | 数据和控制流怎样变化？ | 每跳一层记录：符号、输入类型、输出类型、下一跳理由 | 防止陷入局部实现，看完很多行仍讲不清主链路 |
| **推断** | 没读实现前，我认为它怎样工作？ | 打开源码前写预测；读后标注命中和偏差 | 预测迫使你建立模型；没有预测就无法发现理解缺口 |
| **验证** | 我的结论有何证据？ | 为结论附源码、测试、文档或 Git 历史证据 | 防止把命名直觉和个人猜测当成事实 |
| **压缩** | 能否把复杂代码讲清楚？ | 用一句话、对象图、伪代码或形变表表达 | 能压缩才代表形成结构化理解，而非短期记忆 |
| **迁移** | 换仓库还能否复现？ | 在未读仓库中限时完成相同任务 | 只有迁移成功，才证明学到方法而不是背熟 LangChain |

## 2. 单次阅读算法：QPSVCR

每次打开实现文件前，先按顺序执行以下 6 步。简单问题可压缩到 10min，复杂调用链可扩展到 60min。

| 步骤 | 动作 | 产出 | 为什么 |
|------|------|------|--------|
| **Q · Question** | 把问题写成一句可验证的话，例如「字符串模型名在哪里变成具体类？」 | 1 个问题 | 问题不明确时，阅读会退化为浏览 |
| **P · Predict** | 不打开实现，预测包、类、方法和可能的下一跳 | 1–3 条预测 | 激活已有模型，暴露认知缺口 |
| **S · Search** | 写出搜索策略，再执行搜索：public API → 定义 → 引用 → 测试 | 搜索词与命中路径 | 训练可复用的定位能力，而不是记路径 |
| **V · Verify** | 只读足以证实或推翻预测的最小切片 | 证据行、测试名或调用关系 | 控制阅读范围，避免进入无关细节 |
| **C · Compress** | 将结果压缩成一句话、最多 10 行伪代码、对象图或形变表 | 可复述结论 | 强迫大脑形成结构，而非堆积摘抄 |
| **R · Reflect** | 记录一次命中或误判：错在哪、下次先看什么信号 | 1 条复盘 | 阅读速度提升主要来自减少重复误判 |

### 示例：读 `init_chat_model`

```text
Q：字符串 "openai:gpt-4o" 在哪里路由为 provider 实现？
P：入口应在 v1 chat_models；会拆 provider 前缀；最终动态导入 partner 包。
S：先 rg "def init_chat_model"，再查定义内 provider 分支与调用函数。
V：只读入口、解析逻辑、具体构造调用；暂不追 provider HTTP 实现。
C：字符串配置 → 解析 provider/model → 检查集成包 → 构造 ChatOpenAI。
R：若预测错，记录是包边界判断错、命名判断错，还是跳转顺序错。
```

## 3. 三遍阅读法：先骨架，再链路，最后细节

禁止第一次打开文件就逐行精读。按以下三遍推进：

| 遍次 | 只看什么 | 停止条件 | 原因 |
|------|----------|----------|------|
| **第一遍：骨架扫描** | 文件名、导入、类头、函数签名、docstring、分支标题、返回值 | 能说出文件职责和候选入口 | 先建立索引，否则细节没有挂载位置 |
| **第二遍：问题驱动追踪** | 与当前问题有关的分支、调用点、测试 | 能回答 QPSVCR 中的 Q | 用问题限制阅读范围 |
| **第三遍：风险细读** | 错误处理、边界条件、状态变化、并发、缓存、兼容逻辑 | 能解释关键设计取舍或完成修改 | 细读应由风险触发，而不是默认动作 |

**例外**：安全问题、数据一致性问题、资源释放问题可直接进入第三遍。

## 4. 证据等级：区分事实与推断

所有设计笔记和审核回答必须标注证据等级：

| 等级 | 含义 | 示例 |
|------|------|------|
| **E1 · 直接证据** | 源码、测试或类型签名直接证明 | `BaseChatModel._generate` 是子类实现点 |
| **E2 · 历史证据** | PR、Issue、CHANGELOG、弃用说明解释动机 | 某 API 因兼容策略被替代 |
| **E3 · 合理推断** | 根据结构推测，但没有作者明确说明 | 拆包可能用于降低核心依赖 |

写「为什么这样设计」时，至少提供一个 `E1`；若没有 `E2`，必须明确写「这是我的推断」。

## 5. 每日叠加规则：每个 Day 都必须做

现有日课告诉你当天读什么；以下规则保证你练到阅读能力，而不只是积累 LangChain 知识。

1. 开始前用 3min 写下当天的 **Q** 和至少 1 条 **P**。
2. 打开实现前写出搜索顺序；禁止直接照日课中的文件路径跳转。路径只作为搜索后的校验答案。
3. 每次最多连续读 80 行；超过时先写一句「继续读的理由」。
4. 当天至少写 1 条「暂不读清单」，说明为什么当前问题不需要追进去。
5. 当天输出必须包含一种压缩表达：一句话、对象图、伪代码、形变表四选一。
6. 当天至少记录 1 条命中或误判；没有误判时，记录哪个信号帮助你快速命中。
7. 日志控制在 15min 内，避免训练退化成文档整理。

## 6. 难度递进：逐步撤掉提示

| 周次 | 提示强度 | 执行方式 |
|------|----------|----------|
| **第 1–2 周** | 强提示 | 日课可给文件路径；你仍需先写搜索词，再验证路径 |
| **第 3–4 周** | 中提示 | 只给包和候选抽象，不直接给实现文件 |
| **第 5–8 周** | 弱提示 | 只给公开 API 或行为问题，由你定位文件和下一跳 |
| **第 9–10 周** | 极弱提示 | 只给现象、设计问题或扩展需求 |
| **第 11–12 周** | 陌生仓库 | 不复用 LangChain 路径；限时完成定向、定位、追踪和验证 |

执行日课时，若文档提供的信息超过当前周允许的提示强度，先遮住多余提示，完成预测和搜索后再核对。

## 7. 每周能力仪表盘

每周结束时，不只检查交付物是否齐全，还要填写以下指标：

| 指标 | 记录方式 | 提升信号 |
|------|----------|----------|
| 首个有效入口定位耗时 | 从读题到找到正确入口 | 耗时下降 |
| 无效跳转次数 | 跟错文件或追入无关实现的次数 | 次数下降 |
| 阅读行数 | 为回答问题实际阅读的代码行数，估算即可 | 用更少代码回答同等复杂问题 |
| 预测命中率 | 包、类、方法三级分别统计 | 命中率提高 |
| 证据完整度 | 每条关键结论是否有 E1/E2/E3 | 推断与事实不混淆 |
| 压缩质量 | 能否在 3min 内复述并回答追问 | 表达更短但信息不丢失 |

## 8. 每周随机微测

从第 2 周开始，每周增加一次 `30min` 微测。题目必须来自**本周未精读过**的符号，避免背答案。

1. `5min`：写 Q 和 P。
2. `10min`：定位定义、引用和相关测试。
3. `10min`：读最小切片并压缩表达。
4. `5min`：记录误判与下次策略。

微测只训练阅读动作，不要求形成正式交付物。示例题：

- 给一个陌生 public API，定位其实现入口和一处测试。
- 给一个异常文本，定位最可能抛出异常的位置。
- 给一个扩展需求，定位最小修改面。
- 给一段调用代码，画出前 5 跳及数据类型。

## 9. 毕业标准补充：必须包含陌生仓库和一次小改动

原六项跃升标准继续保留，但毕业时增加两项约束：

1. **陌生仓库验收**：地图、扩展点、主链路至少有一项来自验收当天才确定的未读仓库。httpx 和 LangGraph 可用于训练，不得同时作为唯一毕业样本。
2. **最小改动验收**：在一个已读或陌生仓库中完成一项小修改，补充或调整测试，并说明修改面为什么足够小。限时 90min。

只有“找到、读懂、验证、能改”形成闭环，才能证明源码阅读能力可用于真实工程任务。

# 84 天逐日能力训练矩阵

> 原日课回答「今天接触哪部分 LangChain」；本矩阵回答「今天刻意练哪一种读码能力」。
> 两者必须同时执行。先只看本矩阵的“问题”，完成预测和搜索后，才允许查看原日课给出的路径。

## 0. 设计依据：从当前源码反推训练，不按目录平均分配时间

本计划重点练习以下真实结构，因为它们分别代表常见的源码阅读难点：

| 真实结构 | 本地证据 | 训练价值 |
|----------|----------|----------|
| public API 与实现分离 | `Runnable.__or__` 在 `libs/core/langchain_core/runnables/base.py` 中构造 `RunnableSequence` | 练习从公开操作符定位真实对象图 |
| 抽象类包含默认行为 | `Runnable` 只强制实现 `invoke`；`ainvoke` 默认用 executor 回退 | 练习区分“必须实现”与“框架赠送” |
| 输入类型会逐层形变 | `BaseChatModel.invoke` 将 `str` 转成 `StringPromptValue`，再进入 `generate_prompt` | 练习数据形变表，不只记录函数名 |
| 工厂函数包含多种返回路径 | `init_chat_model` 既可返回具体模型，也可返回 `_ConfigurableModel` | 练习阅读 overload、延迟构造和安全边界 |
| 高层 API 跨仓组装 | `create_agent` 返回 `CompiledStateGraph`，并使用 LangGraph 的 `ToolNode` | 练习识别仓库所有权和停止追踪时机 |
| 同名路径可能只是兼容层 | `libs/langchain_v1/langchain/tools/tool_node.py` 只做 LangGraph 兼容导入 | 练习验证实现所有权，不被文件名误导 |
| 基类同时承担校验与执行 | `BaseTool` 同时包含 schema、输入解析、`invoke`、错误处理 | 练习切片阅读，避免一次吞下大文件 |

## 1. 执行格式

每天从下表取一行，写入日志：

```text
能力动作：
为什么今天练它：
限制条件：
压缩产出：
误判复盘：
```

限制条件是训练的一部分。未经要求，不得直接打开表中“源码锚点”给出的答案路径；锚点用于完成搜索后的校验和 AI 审核。

## 2. 第 1 周：从文档中提取阅读问题，而不是抄摘要

| Day | 能力动作 | 为什么今天练它 | 限制条件与压缩产出 |
|-----|----------|----------------|--------------------|
| 1 | 从根 README 提取 3 个“代码中可验证”的问题，例如模型初始化入口、Agent 入口、与 LangGraph 的边界 | 文档阅读的目的不是记术语，而是生成后续读码问题 | 只读 README；输出“主张 → 待验证问题”表 |
| 2 | 为每个 `libs/*` 包写一句职责，并预测依赖方向 | 先形成包级假设，后面才能发现边界判断错误 | 只读 `libs/README.md` 和目录名；输出包依赖草图 |

# 第一部分：总体方法论与步骤

## 1. 为什么要区分「框架」和「项目」

两者读源码的**目标、入口、顺序、成功标准**完全不同。混用是初学者最常见的失败原因。

| 维度 | 框架（Framework） | 项目 / 应用（Project / Application） |
|------|-------------------|--------------------------------------|
| **本质** | 让别人在此基础上构建 | 解决具体业务问题 |
| **核心问题** | 扩展点在哪？抽象边界在哪？ | 用户请求如何从头到尾走完？ |
| **阅读入口** | README → 公开 API → 基类 / Protocol | main / 路由 / CLI → Service → Repository |
| **阅读顺序** | **外→内**：文档 → 契约 → 组装 → 执行 | **内→外**：入口 → 主链路 → 模块 |
| **文档权重** | 高（代表设计意图） | 中低（常滞后于代码） |
| **测试角色** | 可执行规格 / 合规清单 | 业务回归 |
| **成功标志** | 能实现一个最小扩展 | 能讲清一次完整业务请求 |
| **典型陷阱** | 扎进适配层，忽略抽象层 | 把依赖的框架当黑盒 |

**本次训练聚焦：框架阅读。** LangChain 是典型的「Core 抽象 + 组装 API + Partner 集成」三层框架结构。

## 2. 框架源码六层阅读模型

读任何框架，按以下六层顺序推进。**未完成当前层交付物，不进入下一层。**

```
① 意图层 ── README / Overview / Contributing
     ↓      「作者期望你怎么理解这个框架？」
② 边界层 ── 包结构 / pyproject / __init__ / public API
     ↓      「框架由哪些模块组成？对外暴露什么？」
③ 契约层 ── BaseClass / Protocol / @abstractmethod
     ↓      「用户扩展最少要实现什么？」
④ 组装层 ── Factory / Builder / 管道 / 中间件注册
     ↓      「组件如何被拼成可运行单元？」
⑤ 执行层 ── invoke 调用链 / 状态流转
     ↓      「运行时实际发生了什么？」
⑥ 扩展层 ── 官方 Integration 实现
            「作者认为正确的扩展方式是什么？」

（高阶）⑦ 设计层 ── CHANGELOG / @deprecated / 架构演进
（验证）⑧ 迁移层 ── 换框架，48h 内重走六层
```
